# 搜索策略升级：调研 · 设计 · 接入 · 步骤

对象：open_box 的检索层（现为 `app/plan.py` 的按类别硬编码模板，每条陈述 2–5 条查询、上限 6 次检索）。
目标：把"检索"从**模板填空**升级为**多维差异化策略**，并做到应搜尽搜。

---

## 一、调研：读了什么，学到什么，坚决不学什么

### 1.1 最贴近的一个：HackerRank 开源的 ATS

`interviewstreet/hiring-agent`（MIT，约 3.4k★）。流水线是：

```
PDF → PyMuPDF 转 Markdown → 按 section 分模板让 LLM 抽取（basics/work/education/skills/projects/awards）
    → GitHub API 增强（profile + repos，让 LLM 挑 7 个项目）→ 按 role 评分 → CSV
```

**最值得注意的一点：它完全没有网络搜索。** 唯一的"外部证据"是 GitHub API。
所以"网络搜索逻辑"这件事，这个最主流的开源实现根本没做——这本身是个结论：
**在开源世界里，"把简历陈述拿到公开网上去核"这条路基本没人走通**，现有实现要么只吃 GitHub，
要么（见下）让模型假装搜过。

**它的可取之处**：`roles/<role_name>/` 把评分口径做成**数据目录**——
`role.json`（类别与权重）+ `criteria.jinja` + `system_message.jinja`，
`--init-role` 就能加新职位。**换职位 = 加一个目录，不改代码。**
这正是我们要给"差异化搜索策略"用的形状（见第三节的「策略档案」）。

**它的反面教材**：把评分交给模型。社区实测同一份简历跑 100 次，分数在 **66–99** 之间跳，
`temperature=0` 也稳不住（连带被人扒出 PDF 里塞白字可以刷分——open_box 的
`parse.py` 早就在防这一手了）。这恰好是 open_box「**LLM 只做理解，判定归规则**」最好的论据。

### 1.2 username 枚举类（Sherlock / Maigret / WhatsMyName 生态）

`soxoj/osint-namecheckers-list` 是一份很严谨的横向清单。它们的检索逻辑是：

| 做法 | 说明 |
| --- | --- |
| **username-first** | 拿一个 handle 打 N 个站点，靠 HTTP 状态 + 页面指纹判"存在"，而不是先搜名字 |
| **递归 pivot** | Maigret 从命中的 profile 里再挖出别的账号/邮箱，拿这些**新锚点继续搜** |
| **置信度分级** | 好的实现给分数（Aliens Eye 0–100%、vesper CONFIRMED/LIKELY），不是二值 |
| **站点库与检测分离** | WhatsMyName 只做数据（732 站点 JSON），检测逻辑交给各家——**数据与逻辑分离** |
| **误报率是核心竞争力** | 清单主动标注误报：Maigret「very few false positives 👍」、tookie-osint「~20% false positives 🚫」、social-analyzer「maybe 状态会产生误报 🚫」 |

**迁移到我们场景的关键映射**：中文公开网上**没有可靠的 handle**，所以我们的"锚点"
不是用户名，而是**一对一的稀有标识**——队友姓名组合、队伍名、仓库名、导师名、专利号。
**先定锚、再找经历**，这是第 1 轮检索的全部意义。

### 1.3 招聘 sourcing 的布尔 / X-ray 手法

从业者材料（非代码，但成体系）：

- **分组布尔**：`(标题 OR 同义词) AND (技能 OR) AND (地点 OR) NOT (噪音)`
- **x-ray**：`site:linkedin.com/in …`、`site:github.com …`，绕开平台自身搜索限制
- **平台专属 operator**：GitHub 的 `language:` `location:` `repos:>N` `pushed:>日期`
- **按职级/行业换渠道**：高管看董事会名单、财报、会议议程；一线看本地板；技术看 GitHub / StackOverflow

这三条直接进我们的设计：查询**分层语法**、**域名限定做一等参数**、**按层级换来源**。

### 1.4 Google dork 五件套

`site:` / `intitle:` / `inurl:` / `filetype:` / `cache:`。
我们在允许范围内用前四个（`cache:` 依赖搜索引擎缓存，不做）。

### 1.5 明确不学的四件事

1. **让模型"模拟搜索"。** 有项目明写「模型會模擬搜尋公開資訊」——那是编造出处。
   open_box 的第一原则就是"查不到就说查不到"，这条直接违反。
2. **让模型出分数。** 见 1.1 的反面教材。我们的判定层零模型调用。
3. **OSINT 的人身档案套路。** 社交关系图谱、住址、电话、照片地理定位、泄露库
   （HIBP / IntelX）、车牌、行为画像——open_box 明令不做。**我们的对象是陈述，不是人。**
4. **高误报的暴力枚举。** 清单自己把 20% 误报标成 🚫。同名误认是本产品的红线，
   我们宁可少找、标"未找到"，也不认错人。
5. **绕限制**：代理池、验证码破解、cookie 抓取、搜狗微信绕行——全部不做。

## 二、接入方式

### 2.1 三个层次，各自的可替换点

```
策略层（规则，open_box）        策略档案 JSON + 解析器        ← 本次新写
   ↓ 产出带优先级/要素/来源的 Query Plan
执行层（适配器，open_box）      search.py 的 provider          ← 本次扩充
   ↓ 一次搜索 = 一个域限定 + 一组词
供应商（外部 API）              智谱 / 博查 / Serper           ← 需要 key
```

### 2.2 搜索供应商：需要你提供一个 key

open_box 的 README 已经论证过选**智谱 Web Search**，理由是
`search_domain_filter` 是**一等参数**，正好对上我们的 `search(query, site=)`，
不用把 `site:` 拼进查询串（拼进去是否生效取决于引擎，不可控）。

适配层会同时支持：

| 供应商 | 环境变量 | 备注 |
| --- | --- | --- |
| 智谱（默认） | `SEARCH_API_KEY` + `SEARCH_ENGINE` | `search_std` 便宜、`search_pro` 覆盖好 |
| 博查 Bocha | `SEARCH_PROVIDER=bocha` | 字段干净，含 `datePublished` |
| Serper | `SEARCH_PROVIDER=serper` | 便宜、Google 语法全，中文高校深层页弱 |
| 通用 | `SEARCH_PROVIDER=generic` + `SEARCH_ENDPOINT` | 自建网关 |

**没有 key 我也能做完**：策略引擎、Query Plan、覆盖度自检全部可以用 fixture 搜索器验穿，
只是不能真跑。给我 `SEARCH_API_KEY` 就能立刻切到真实检索。

### 2.3 LLM 侧已经配好

DeepSeek 已可调用（`~/.dsh/.credentials.yaml` / `open_box/.env`），
并且修掉了"带思考模型吃光 max_tokens"的坑（`LLM_THINKING=disabled`）。
本方案里模型只负责**理解**：读简历产出 profile（身份/行业/层级/技能），
不参与任何"要不要再搜一条""这条算不算证明了"的判断。

## 三、搜索策略设计

### 3.1 五个维度

| 维度 | 取值 | 它决定什么 |
| --- | --- | --- |
| **身份类型** identity | student / professional / researcher / creator / public_sector | 主战场在哪（校内公示 vs 公司官网 vs 知网/Crossref vs 平台主页 vs 政府公告） |
| **行业** industry | internet / finance / healthcare / education / manufacturing / legal / media / gov | 权威源是谁（证监会披露 vs 卫健委公示 vs 学校官网） |
| **层级** level | intern / entry / mid / senior / lead / exec | 该不该找媒体与披露（高管有专访和公告，实习生几乎只有校内记录） |
| **技能/资质** skills | tech stack、证书（CFA/CPA/执业医师/教师资格）、工具 | 追加"可验证的专有名词"查询：证书编号、项目名、技术栈 |
| **陈述类别** category | 现有 10 类 | 要素怎么拆、找哪类文档 |

前四个由模型从简历里读出来（理解），第五个是陈述自带的结构。

### 3.2 策略档案：数据，不是代码

照 hiring-agent 的 `roles/` 形状，把"什么简历该去哪搜"做成 JSON 档案
（`data/strategies.json`），**加一种简历类型 = 加一个档案，不改代码**。

```jsonc
{
  "id": "cn-university-student",
  "name": "中国大陆在校生",
  "match": {
    "identity": ["student"],
    "levels": ["intern", "entry"],
    "categories_any": ["校内荣誉", "奖学金", "学生工作", "竞赛"]
  },
  // 权威源画像：这类陈述"由谁发布"，而不是"用什么关键词"
  "authority_map": [
    { "who": "学校学生工作部",  "host": "<校域名>",          "expect_tier": "A", "what": "评奖评优公示" },
    { "who": "学院官网",        "host": "<校域名>",          "expect_tier": "A", "what": "院级公示" },
    { "who": "竞赛组委会",      "host": "<organizer_domain>", "expect_tier": "A", "what": "获奖名单" },
    { "who": "学校/学院公众号", "host": "mp.weixin.qq.com",  "expect_tier": "B", "what": "换届公告" }
  ],
  // 先定锚：中文场景没有 handle，用一对一稀有标识
  "anchor_first": ["队友姓名组合", "队伍名", "仓库名", "导师姓名"],
  "budget": { "searches": 8, "reads": 10, "seconds": 120 },
  "notes": "校内任免与评奖多数只在学校官网公示；公众号只能吃搜索引擎已收录的部分"
}
```

### 3.3 Query Plan：每条查询都必须说出它为什么存在

现在的 `Query` 只有 `text/site/kind`。升级后每条查询要挂上：

```jsonc
{
  "text": "晴川大学 校学生会 科技部 换届 2024",
  "site": "xsc.qingchuan.edu.cn",
  "kind": "web",
  "element": "职务=部长",              // ← 它在证明哪个要素（没挂要素的查询不该发出去）
  "purpose": "找换届公告里科技部的任命",
  "expect": { "tier": "A", "publisher": "校学生工作部" },
  "round": 2,                          // 1 定锚 / 2 取证 / 3 补漏
  "weight": 90
}
```

`element` 这个字段是关键：**查询必须挂在要素上，不能挂在陈述上。**
"证明了任职组织 ≠ 证明了职务"这条设计，往上追一层就变成
"为每个未证要素各配一条查询"。

### 3.4 三轮递进（"应搜尽搜"的结构化表达）

| 轮 | 干什么 | 为什么 |
| --- | --- | --- |
| **1 定锚** | 用稀有标识确认"网上的这个人是本人"：队友姓名组合、队伍名、仓库名、导师名 | 锚点定不住，后面全是同名噪音。这是从 namechecker 的 `username-first` 迁移过来的 |
| **2 取证** | 锚点 + 要素，按 `authority_map` 逐个域限定搜 | 一条一条地证，而不是撒网 |
| **3 补漏** | 覆盖度自检后，对**没有任何查询覆盖的要素**补搜：换同义词、放宽到公众号/媒体 | 补漏的触发条件是**规则算出来的**，不问模型"够不够了" |

### 3.5 覆盖度自检：应搜尽搜真正落地的地方

一轮跑完，逐要素过一遍：

| 情况 | 动作 |
| --- | --- |
| 某要素**一条查询都没覆盖** | 必须补搜（这是覆盖率缺口，不是"查不到"） |
| 有查询、零结果 | 换同义词 / 放宽域名 / 换媒介（公众号、地方媒体），仍无则如实记 `none` |
| 已拿到证据但要素未证 | **针对性补搜**：如"只证明了任职组织，那就专门搜职务" |
| 要素已证但来源等级 < B | 按达标要求补搜更高等级来源 |

这张表**由规则判定**，和 `judge.py` 同一条纪律。跑完输出一份覆盖度报告：
哪些要素被几条查询覆盖、哪些是缺口——这样"应搜尽搜"是可核查的，而不是一句口号。

## 五、这次要守住的三条

1. **策略是数据，判定是规则，只有理解交给模型。** 换行业/职级 = 加一个 JSON 档案；
   "够不够了""算不算证明了"永远由规则回答。
2. **查询必须挂在要素上。** 一条查不出任何要素的查询，是浪费预算。
3. **宁可少找，不认错人。** 锚点定不住就如实标"未找到公开记录 / 身份未确认"，
   不为了覆盖率好看而放宽到同名即可。覆盖率只反映公开信息的多少，不是可信度。

## 六、实现中发现并修掉的问题

写引擎的过程里揪出五个真问题，其中三个是**原版就有的**：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `orgname = dept or org`，而 `dept` 往往只是**部门** | c05 的 org='晴川大学校学生会'、dept='科技部' → 第一条查询变成 `"科技部" 换届 2024`，**组织名整个丢了** | `_qualify()` 拼全称 → `"晴川大学校学生会科技部"` |
| 2 | 占位符只从 `entities` 取值，而 `entities` 是模型填的、不保证有 | c04（竞赛）entities 里没有 `contest` → 展开出 `"" 2023 获奖名单` 这种**空引号查询** | 加 `elements_map`：**entities 优先、elements 兜底**（elements 是拆分步骤保证会有的）；并在展开前就检查占位符有没有值 |
| 3 | 有的模板精确性**完全靠 site 限定** | 赛事组委会的 `{year} 获奖`，拿不到组委会域就退化成 `2023 获奖` 这种烂查询 | 表单显式声明 `requires_site`，域拿不到就不发 |
| 4 | `categories_any` 被当成**逐条陈述的过滤器** | 在校生简历里的论文/开源项目匹配不上在校生档案，掉到兜底（预算 8→6）。**这是我自己第一版的缺陷** | 改为对着**整份简历的类别集合**判——它的本意是"这份简历像不像在校生" |
| 5 | 档案追加查询无类别限定 | 「互联网职场人」的 GitHub/技术分享查询套到「校内荣誉」上，生成 `"林昱和" 晴川大学 技术 分享` 这种纯噪音 | 表单可声明 `categories`；`categories_any` 同时用于两个用途（简历级匹配 + 该档案的追加查询该发给哪些类别） |

**修完之后各画像的总查询数分开了**（同一份简历实测）：

| 画像 | 查询总数 |
| --- | --- |
| 在校生 | 53 |
| 互联网职场人 | 44 |
| 科研人员 | 41 |
| 兜底（识别不出） | 39 |

兜底最低是对的：**不知道去哪找时，广撒网只会烧预算换噪音。**

### 预算：默认值与硬天花板是两回事

原版 `MAX_SEARCHES = 6` 同时当默认值和上限用。差异化策略的意义恰恰是"该多搜的简历多搜"
（金融/科研类中层以上任职确有公开权威记录），所以拆成：

- `MAX_SEARCHES = 6` —— **默认**（档案没指定时用），`collect.Budget` 也用它
- `CEILING_SEARCHES = 12` —— **硬天花板**，任何档案都不能突破

没有天花板的话，一个写错的档案就能把成本放大十倍。

**并且执行层必须照计划带的预算走**：`Plan` 现在自带 `budget`，`pipeline` 用它构造 `Budget`。
档案说 8 次检索、而 `collect` 仍用默认 6 的话，多出来的两条查询永远不会执行，
**差异化策略就成了装饰**。

例外：调用方**显式传了 `budget_factory`** 时完全照它走（验收第 18 项就是用它把预算压到 1 次
来跑断路场景）——"你给了预算工厂，预算就归你"。

## 七、真实简历验证（在校生案例）

拿一份**真实的**在校生简历（本机样例，未随仓库分发）跑通了整条流水线（真实 DeepSeek + 新策略引擎，
搜索因缺 key 走 NullSearcher → 全部如实 `none`）。**总耗时 17 秒。**

### 它揪出了三个只有真实数据才会暴露的 bug

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | **输出被 max_tokens 截断**。这份简历被拆成 31 条陈述、输出 11691 字符，在 4096 token 处拦腰截断 | JSON 是半截的，报错却是"模型输出不是合法 JSON"——完全误导排错方向 | `complete_json` 自愈：`finish_reason=length` 时**加倍预算重试**（实测 deepseek-flash 接受到 32000）。`max_tokens` 只是上限不是成本（按真实输出计费），放开不花钱 |
| 2 | **过度拆分**：31 条陈述，5 个竞赛拆成 8 条、一段实习拆成 9 条 | 理论预算 31×8=248 次检索，成本爆炸；且大量碎片没有任何可搜实体 | 改写拆分粒度：**一条陈述 = 一段可独立核验的经历**，不是一句话里的每个事实；上限 12 条；每条必须有可检索实体 |
| 3 | 拆分提示词里那句"一句话含多个可证伪事实就拆成多条"+ 拆成 5 条的例子 | 正是 #2 的源头。对 fixture 是对的，对真实简历是灾难 | 删掉，换成"要点留在 raw_text 里由要素核对处理" |

另修两个拆分质量问题：**学历把奖学金吞了**（学历不检索 → 那条奖学金永远不会被搜）；
两个**不同赛事被合并成一条**（合并后的"赛事A / 赛事B"没法作为检索词）。

### 修完之后的效果（同一份简历）

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| 陈述数 | 31 | **9** |
| 其中 0 条查询的 | 19 | **1**（学历，按设计） |

## 九、网页端接真实数据（去 mock）

`serve.py` 新增 `/api/verify`：浏览器把文件**原样** POST 过来（body = 文件字节，
`X-Filename` 带文件名），服务端跑 open_box 流水线，`to_presentation()` 转成网页端的
REPORT 形状返回。**前端渲染逻辑一行没改**——它本来吃的就是这个形状，现在换成真数据。

```sh
python3 serve.py      # 打开 http://127.0.0.1:8787/，拖入简历就是真实核验
```

| 徽标 | 含义 |
| --- | --- |
| **LIVE · 真实核验** | 模型 + 搜索 key 都配好了 |
| **LIVE · 未配搜索 key** | 模型在跑、检索为空 → 提示条会如实写"本页检索为空"，所有陈述如实标 `未找到公开记录` |
| 演示数据 · 均为虚构 | 从 `file://` 直接打开（没有后端），才用本地 fixture |

MOCK 徽标退役。**真数据的成本当前是 15 秒/份**（9 条陈述），全部花在模型调用上。

联调揪出的三个 bug（都写进代码注释了）：

1. **中文文件名做 HTTP header** → `fetch` 抛 "Failed to execute 'fetch'"（Invalid header value），
   报错完全看不出是文件名的问题。头里传非 ASCII 必须 `encodeURIComponent`。
2. **沙箱的文件代理对 `mkdir(已存在目录)` 抛 PermissionError(EEXIST)** → 第一次请求成功、
   之后每一次秒失败，浏览器只报 "Failed to fetch"。临时文件用**系统临时目录**。
3. `applyFilter()` 必须在 `renderClaims()` **之后**跑，否则计数显示 0/N。
